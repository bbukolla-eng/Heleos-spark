# CSI Division 23 work breakdown

The [master plan](../superpowers/plans/2026-09-16-division23-section-delivery.md)
follows the complete verified **April 2016 CSI/CSC** hierarchy: Division root,
14 direct branches and every listed section/subsection. The canonical
[register](division-23-section-register.json) supplies exact number/title/parent/
child identities and source pages. Current-2026 reconciliation is separate;
no agency-guide hierarchy or speculative crosswalk is active.

## What is planned at each CSI address

Every one of the 432 nodes has a card and four explicitly planned task frames:

| Frame | Required deliverable | Finish line |
| --- | --- | --- |
| `<CSI-id>-DEFINE` | Mechanical source inventory, complete declared taxonomy, applicable approved rules, independent expected cases and bounded implementation packets | D01–D06 pass for the declared source-definition scope; any missing referenced input remains an explicit scoped gap and unready behavior |
| `<CSI-id>-RESULT` | Source-linked deterministic quantities or supported obligations for admitted scope | R01–R06 pass on frozen independently expected cases |
| `<CSI-id>-CONNECT` | Mac review/reconciliation, corrections, revisions/reopen and Excel/evidence-PDF workflow | C01–C08 pass with real application and artifact evidence |
| `<CSI-id>-QUALIFY` | Complete required section scope and descendants on fixed representative source projects | Q01–Q05 and all required SC01–SC08 coverage pass; the matching `<CSI-id>-ACCEPT` address may close |

Exact criterion text/bindings live in [the task index](division-23-task-contracts.json)
and [shared specification](../superpowers/specs/2026-09-16-division23-section-task-contracts.md).
There are 1,728 task frames; none becomes a ready coding assignment merely because
its title and acceptance suffixes exist.

## Full mechanical taxonomy and child scope

For the selected section, enumerate required types, variants, attributes,
relationships, exclusions, physical assemblies/components and services. Record
each adopted source clause and applicable option, referenced-document dependency,
lifecycle and supply/installation boundary. Do not invent a Cartesian product
of every possible size/material/joint or adopt requirements from a heading alone.
The declared source-supported variant set is explicit and reviewable.

A stable taxonomy record includes `id`, `section_id`, `kind`, `parent_taxon_id`,
`required`, `attributes`, `relationships`, `source_refs`, `rule_bindings`,
`case_ids` and `coverage_receipts`. Each independently testable family/child task
names its admitted taxonomy IDs, actual output dependencies and inherited
criterion IDs. Supporting calculation/recognition/reconciliation components may
serve several sections, with explicit evidence bindings and no double counting.

Parent completion requires all required own taxonomy and descendant evidence.
It aggregates accepted children rather than repeating them. A catalogue entry
with no listed children still requires its full declared mechanical taxonomy;
“leaf in catalogue” is not synonymous with “one material count.”

A nonphysical service has supported obligations, responsibility/document evidence
and relevant workflow/export tests. UNKNOWN records its source, missing input,
affected results, next action and resolution history. UNKNOWN is not zero;
a referenced document is not a supplied document; repeated drawing/schedule/spec
appearances are not additional physical objects.

## Dependencies and expected results

Before dispatch, bind one deliverable to exact source/rule/fixture identities,
actual interfaces, named code/test paths and one writer. Each dependency names a
producer output and accepted scope, not merely an entire prior phase. Freeze
independent expected counts/identities/exception states and measurement tolerance
before evaluation. Recognition has its own original-source metrics and qualified
scope. Preserve the already approved D/A/E rules and imperial basis.

Missing source bodies, estimating decisions, fixture truth or interface knowledge
get `<CSI-id>-INPUT-<gap-id>` tasks with finite resolution conditions. They block
only dependent behavior. A correct gap list does not close unresolved required
mechanical scope. New scope/editions create explicit contract extensions.

## Scheduling and handoff

Root `CURRENT_STATUS.md` remains the single live queue. Catalogue numeric order
is navigation and coverage, not a serial implementation gate. Mac is first;
Windows delivery is separate. Preserve existing equipment implementation priority
and accepted shared support without making them the entirety of Division 23.

Workers report candidate identity, checks and terminal outcome within named write
paths. Codex independently verifies, integrates and updates root status with the
accepted result and next executable action. No worker commits or promotes its
own output. No recurring metadata task or scheduler is created by this breakdown.
