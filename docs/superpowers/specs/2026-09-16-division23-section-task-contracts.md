# Division 23 section task and acceptance contracts

This specification implements the owner's explicit request to plan **each of the
56 supplied guide rows**, every task and its acceptance, and keep the plans in the
active project entrypoints. It supersedes the former implication that a matrix of
planned stage slots or a maintenance-tool plan is the section delivery plan.

## Global Constraints

- Mac is the current implementation and section acceptance target; Windows delivery is separate.
- Preserve approved D01–D10, A01–A12, E01–E12 and imperial outputs; new quantity policy needs its own recorded decision.
- A section means its complete declared source-backed taxonomy, including physical work, services, exclusions and required children.
- Guide identity and project adoption remain distinct; agency numbers do not establish an unverified CSI hierarchy.
- Reuse accepted evidence for unchanged inputs; new requirements create explicit extension tasks or contract versions.
- Codex is the only commit owner; each worker has exact named write paths and returns a candidate.
- Use verified NotebookLM source passages before knowledge-dependent implementation; log external submissions and preserve source identities.
- The cancelled 4specs adoption remains cancelled; an illustrative example does not select a priority.
- No new hook, scheduler, provider access, push or release is authorized by this plan.

## Deliverables and boundaries

1. One master section execution index and one detailed plan per known guide row.
2. Four independently reviewable deliveries per section: DEFINE, RESULT, CONNECT,
   QUALIFY. These yield **224 named delivery contracts**, separate from the 448
   existing SC coverage addresses. A discovered independently testable family may
   get child tasks with explicit scope; do not require four tasks per taxon.
3. Each task records exact section/edition scope, concrete output paths, consumed
   outputs and conditions, criterion IDs, check procedure, reviewer and terminal
   evidence. No unspecified global “acceptance” gate remains in the task sequence.
4. Every required type/variant/relationship/obligation remains covered, including
   references, exclusions, service work, temporary/spare materials and execution
   requirements. Title-derived subjects are source-enumeration questions, not
   adopted taxonomy or calculation rules.
5. Unavailable guide bodies, new estimating policies and representative fixtures
   are explicit inputs to definition work. They cannot be replaced by invented
   quantities, source passages or numerical accuracy targets.
6. No new product engine, source adoption, model run, quantity rule, whole-section
   acceptance or platform acceptance is delivered by this planning change.

## Meaning of acceptance

**Task acceptance is a recorded pass of every mandatory criterion in a fixed,
versioned contract, on identified inputs and candidate bytes, independently
reviewed and integrated.** It has a finite checklist. “No unresolved failures”
means none of those mandatory comparisons remain outside their expected result;
it does not mean there can be no future defects or unfinished work elsewhere.

A source-definition task can finish when it accurately accounts for the primary
source and names unresolved referenced inputs/rules. Its accepted outputs release
only ready, hash-bound cases. That does not complete required missing taxonomy,
freeze an unprovided expected value or accept dependent numeric behavior.

A missing primary guide body fails DEFINE's body/coverage criteria. A missing
referenced document is an explicit dependency with affected scope, a responsible
next action and owner; it is not silently treated as supplied. The section itself
cannot close while mandatory taxonomy, rule or behavior gaps remain.

An expected UNKNOWN or source-conflict result can pass its named exception case.
A case requiring a supported quantity cannot pass by substituting UNKNOWN. New
requirements or stricter targets get extension tasks/contract versions; review
preferences do not move an accepted finish line.

## Acceptance records

Every task's receipt records: task ID, contract version/hash, declared scope,
input/source/rule/fixture identities, candidate manifest, case and criterion IDs,
actual versus expected results, tolerances, exact check exits, evidence paths,
independent reviewer, integration identity and next action. A nonempty mandatory
case set is required; skipped/unrun checks cannot be marked pass.

Exact counts, identity sets, source links, known/unknown state and historical
records compare exactly. Measured quantities compare only under a numeric
case-specific tolerance fixed before execution. Source recognition and allowed
review burden use a separately frozen original-source set and metrics. Field
TAB, manufacturer or code performance limits are not automatically software
accuracy thresholds.

## Scope of each section's four deliveries

| Task | Independent output and endpoint | Dependence that may actually block it |
| --- | --- | --- |
| DEFINE | Full primary-source map/taxonomy, rule bindings, independent cases or named missing-input actions, admitted code/test implementation packets; D01–D06 pass | The exact primary body and source review; missing downstream policy blocks only its cases |
| RESULT | Deterministic source-bound quantities/obligations for admitted scope; R01–R06 pass | Required approved rule and frozen case outputs; no blanket dependency on model qualification |
| CONNECT | Real section review/reconciliation, correction/revision/reopen and Excel/PDF behavior; C01–C08 pass | The exact source/accepted result outputs consumed by each behavior; evidence-only work may precede numeric outputs |
| QUALIFY | Complete required section taxonomy and SC01–SC08 pass on frozen original-source representative Mac cases; Q01–Q05 pass | Full required scoped evidence, representative truth/thresholds and actual Mac candidate |

Four delivery boundaries are not a requirement to implement a large guide in one
patch. DEFINE records child implementation tasks where separate source-supported
families can be independently tested/reviewed. Each child inherits named criteria
and only its required outputs. Accepted children remain closed while siblings
advance; parent closure aggregates the entire required scope.

## Persistent routing

- `CURRENT_STATUS.md`: single live primary task and ready independent actions;
  its first section-plan link points to the master execution index.
- `docs/plans/division-23-task-contracts.json`: planned task specification and
  exact section bindings. Criterion templates are expanded by each section card.
  Planning states are a dated baseline, not another live scheduler.
- `docs/superpowers/plans/division23-sections/`: complete per-section work cards.
  All cards carry their actual scope, inputs, paths, cases, criteria and endpoints.
- `docs/plans/division-23-section-register.json`: source identities, coverage
  state and plan/task links. The completion matrix remains its readable view.
- The selected task's existing ledger: live execution state, frozen candidate
  inputs, real results/reviews and completion receipt; root status links it.

At completion, Codex records the terminal receipt, maps exact accepted output to
covered cells, updates the section coverage/register/matrix and current next
work in the same completion commit. Keep plan contracts versioned; do not rewrite
historical expected outcomes to match actual failures. Future source additions
receive an equivalent linked section plan before dependent implementation.
