# Skills, agents, plugins, and MCP servers: admission register

**Status:** Proposed for owner review (revision 2)
**Date:** 2026-09-02
**Owner:** Bekim Bukolla
**Supersedes:** the 2026-09-01 register on pull request #3
**Governs:** every skill, agent pack, plugin, MCP server, coding harness, workflow script, and generated configuration used with Heleos-spark

Design spec section 11 makes skills and plugins executable supply chain: admission requires provenance, a pinned version or digest, a license, a permissions and egress review, evaluation evidence, a named owner, a concrete task, and a rollback target. Nothing on this page is admitted by being listed. Each row carries a status; only the owner moves a row to **Admitted**, by a record under `docs/decisions/`.

What changed in revision 2: every row was checked against the execution environment on 2026-09-02 (see [`phase-0-evidence.md`](phase-0-evidence.md) section 7). Commit pins carried over from revision 1 for tools that are absent here are owner-asserted and marked unverified until the owner checks each at admission. Tools that revision 1 cited by machine-local path do not exist in a fresh Claude Code Remote session, so the register now distinguishes what the harness provides, what the repository owns, and what would have to be installed and reviewed. The owner and evidence columns the admission checklist requires are added.

Statuses: **Authorized by spec** (section 11 names it), **Harness-provided** (part of Claude Code or its connectors; version follows the harness, recorded as an accepted exception to the pinning rule), **Repository-owned** (versioned and tested in this repository), **Proposed: Phase N** (needed from that phase; not yet admitted), **Reference only** (read for patterns; nothing installed), **Not authorized** (present or generated but unreviewed; must not run as-is), **Absent** (named by revision 1 but not present anywhere; listed so the dependency is visible).

## 2. Accepted exceptions to the pinning rule

Harness-provided components (the Claude Code tools, the four connectors, the account-synced skills) cannot be pinned by the repository; their version follows the harness. The operating model records the harness version in every run record and forces a `harness-probe` re-run when it changes. This exception is recorded here so that it is a decision, not an omission, and it is listed in `docs/runs/KNOWN-LIMITS.md` once that file exists.

## 4. Admission checklist (copy per tool into `docs/decisions/`)

1. Source reviewed at the pinned commit; no runtime fetch of unpinned code.
2. License recorded and compatible.
3. Permissions and egress listed; data classes it may touch named (spec section 5).
4. Concrete task and named owner.
5. Evaluation evidence: what was tried, on which fixture, with what result (a `docs/runs/` record where a workflow was involved).
5a. Documented, supported APIs only: an undocumented or experimental endpoint may be a laboratory adapter behind a capability test, never a required dependency (spec section 9).
6. Rollback target: the exact command or file revert that removes it.
7. Owner approval recorded with date.
