# Grok working instructions

This file governs coding-capable Grok routes such as an available CLI, API, or adapter. It does not govern the separate GrokBots macOS application. Shared policy lives in [AGENTS.md](AGENTS.md), the dated status snapshot in [CURRENT_STATUS.md](CURRENT_STATUS.md), and workflow routing in [SKILLS.md](SKILLS.md). If a runtime cannot confirm loading, supply the approved instruction context explicitly with the bounded task and respect its egress scope.

Before use, identify the concrete Grok route and verify its real capabilities, authentication, checkout, and write boundary. Do not guess commands, assume an account session, or infer that a research/chat surface can edit files. These instructions are not enforcement, a sandbox, or evidence that any Grok tool is installed, authenticated, or automatically loaded.

A verified write-capable route may receive one isolated assignment: exact base identity, owned source and test paths, required checks, and a clear stopping condition. It may produce a narrow candidate patch, tests, or supporting documentation. It must preserve unrelated changes and report the exact files touched, commands run, results, limitations, and any unverified claims. It has no standing authority to merge, push, deploy, expand scope, or self-approve; the controller reviews the bytes and reruns proportionate checks.

Grok may also perform public-first research or adversarial design review. Research deliverables must distinguish sourced facts, inference, and recommendations, with working citations and retrieval context. Never fabricate citations or present model recall as verified evidence.

Never send secrets or credential material. Internal code, confidential evidence, or private project data requires the applicable project/provider approval. Minimize submitted context. All code, test results, citations, and capability claims remain candidates until independently checked.
